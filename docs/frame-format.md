# フレーム形式(版 1)

XIAO RP2040 のファームウェアが PC(ブラウザ)へ送るバイナリメッセージの定義。この文書が正で、ファームウェアの実装(`src/frame_proto.c`)とテストベクタ(`docs/frame-vectors.json`)はこれに従う。受信側はこの文書とテストベクタだけで実装できるように書いている。

## 全体の構成

2 つの層に分ける。

1. **ペイロード**(経路に依存しない): 1 つのメッセージ。先頭にマジックと版、種別があり、種別ごとの本体が続く
2. **リンク層**(経路ごと): ペイロードの後ろに CRC-32 を付けたもの(以下「パケット」)を、経路に合わせて包む
   - USB シリアル(いまの実装): パケットを COBS でエンコードし、区切りとして 0x00 を 1 バイト付ける
   - WebSocket / UDP(将来の予定): 1 つのメッセージにパケットをそのまま入れる(COBS と 0x00 は付けない)

```
ペイロード  = 共通ヘッダ(12 バイト) + 種別ごとの本体
パケット    = ペイロード + CRC-32(ペイロードに対する値、リトルエンディアン 4 バイト)
USB シリアル = COBS(パケット) + 0x00
```

## 数値の表し方

- 多バイトの整数はすべて **リトルエンディアン**
- 型の表記: `u8` / `u16` / `u32` は符号なし、`i8` / `i16` は 2 の補数の符号付き
- 境界の詰め物(パディング)はない。配列も前のフィールドの直後から始まる(2 / 4 バイト境界にそろっていない位置から多バイトの値が始まることがある。JavaScript では `DataView` の `getInt16(offset, true)` などで読む)

## 共通ヘッダ(全種別)

| オフセット | 型 | 名前 | 値 |
|---|---|---|---|
| 0 | u8[2] | magic | `0x56 0x38`(ASCII で `V8`) |
| 2 | u8 | version | `1` |
| 3 | u8 | type | `1` = 測距フレーム、`2` = ログ、`3` = 状態 |
| 4 | u32 | seq | シーケンス番号(下記) |
| 8 | u32 | timestamp_us | 送信側の起動からの時間 [µs] の下位 32 bit(下記) |

### シーケンス番号

- 種別によらず、送信側がメッセージを 1 つ送るたびに 1 増える(起動から通しの値。モードを切り替えても 0 に戻らない)
- 2^32 で 0 に折り返す
- 受信側は、**最後に受け付けた**メッセージの seq を `prev` として、次に受け付けたメッセージとの差 `d = (seq − prev − 1) mod 2^32` を見る
  - `d = 0`: 欠落なし
  - `1 ≤ d < 2^31`: d 個のメッセージが欠けた(「欠落」1 回、欠落数 d)
  - `d ≥ 2^31`: 欠落ではなく番号が戻った(「後退」1 回。送信側の再起動や記録の継ぎ目)
  - どの場合も、その後は `prev = seq` にする
- 拒否したパケットや長さ 0 のパケットでは `prev` を変えない(リセットもしない)。拒否したパケットの分は、次に受け付けたメッセージとの差で欠落として数えられる
- 最初に受け付けたメッセージは比較しない
- seq が数えるのは**送信側が送ろうとしたメッセージ**の欠落(USB 上で捨てられた・壊れたもの)。センサーのフレームをファームウェアが読めずに取りこぼした場合(下記「送信側の制約」)は、メッセージ自体が作られないので seq は飛ばない。センサー側の取りこぼしは、**測距フレームの timestamp の間隔**(頻度 15 Hz なら約 66.7 ms。取りこぼすとその倍数に近い間隔になる)で見る

### タイムスタンプ

- 測距フレームでは、センサーのデータの準備を検出した時刻。ログと状態では、組み立てた時刻
- 約 71.6 分(2^32 µs)で 0 に折り返す。間隔は `(t2 − t1) mod 2^32` で求める

## 種別 1: 測距フレーム

### ヘッダ

| オフセット | 型 | 名前 | 値 |
|---|---|---|---|
| 0〜11 | | 共通ヘッダ | type = 1 |
| 12 | u8 | side | 一辺のゾーン数。`4`(4x4)または `8`(8x8) |
| 13 | u8 | targets_per_zone | ゾーンあたりターゲット数 T。`1`〜`4`(いまのファームウェアは 1) |
| 14 | u16 | field_mask | 含むフィールドのビットマスク(下記) |
| 16 | i8 | temperature_c | センサーの温度 [℃] |
| 17 | u8 | reserved | `0` |
| 18〜 | | フィールドの配列 | field_mask のビットが小さい順に、含むフィールドの配列を続けて並べる |

ゾーン数を Z = side × side とする。

### フィールド

| ビット | 名前 | 要素の型 | 単位 | 要素数 | 内容 |
|---|---|---|---|---|---|
| 0(`0x0001`) | distance_mm | i16 | mm | Z × T | 距離。ステータスが有効でないゾーンの値は意味を持たない(負になることもある) |
| 1(`0x0002`) | target_status | u8 | — | Z × T | 測距ステータス(ST の ULD の値そのまま)。**5 と 9 が有効**(ULD の説明 "5 & 9 means ranging OK")。**255 はターゲットなし**。ほかは無効。起動直後の 1 フレーム目は 6 / 13 になる(実機で確認) |
| 2(`0x0004`) | range_sigma_mm | u16 | mm | Z × T | 距離の標準偏差の推定値。大きいほど距離の信頼性が低い(実機で有効なゾーンの中央値は 10〜11 mm) |
| 3(`0x0008`) | nb_target_detected | u8 | 個 | **Z** | そのゾーンで検出したターゲット数(**ゾーンごと**。ターゲットごとではない) |
| 4(`0x0010`) | signal_per_spad | u32 | kcps/SPAD | Z × T | 戻ってきた信号の強さ(SPAD 1 個あたりの毎秒のカウント数 ÷ 1000)。ULD が 2048 で割って整数にした値。反射率と距離で変わる(「IR 画像」として表示できる) |
| 5(`0x0020`) | nb_spads_enabled | u32 | 個 | **Z** | そのゾーンの測距で有効にした SPAD(受光素子)の数(**ゾーンごと**)。ULD のヘッダ(`vl53l8cx_api.h`)の説明は "Number of spads enabled for this ranging" と、ゾーンごとの結果(全ターゲットに共通)であることだけ。ULD は変換せずにそのまま渡す。センサーが対象の遠さ・反射の強さに応じて有効にする SPAD の数を変える(返りが弱いほど多くする)かどうかは、ST の資料では**未確認**(実機の値で確かめる) |
| 6〜15 | (予約) | — | — | — | 版 1 では使わない。**立っていたら拒否する**(配列の長さが分からないため)。将来、反射率・周囲光などを足すときは版を上げる |

いまのファームウェアは 8x8、T = 1、field_mask = `0x003F`(全フィールド)を送る。

#### 配列の並び

- 各配列の添字は、ターゲットごとのフィールドが `zone × T + t`(t = 0〜T−1。t = 0 が最初のターゲット)、ゾーンごとのフィールド(nb_target_detected、nb_spads_enabled)が `zone`
- `zone = row × side + col`(row, col = 0〜side−1)。ST の ULD の並びそのまま
- 各配列の後ろに次の配列が隙間なく続く。ペイロードの長さは次の式とちょうど一致しなければならない

```
18 + Z×T×2 (bit0) + Z×T×1 (bit1) + Z×T×2 (bit2) + Z×1 (bit3) + Z×T×4 (bit4) + Z×4 (bit5)   ※ 含むビットの項だけ足す
```

例: 8x8、T = 1、`0x003F` → 18 + 128 + 64 + 128 + 64 + 256 + 256 = **914 バイト**。4x4、T = 1、`0x0003` → 18 + 32 + 16 = 66 バイト。

#### ゾーンと物理的な向き

## 種別 2: ログ

| オフセット | 型 | 名前 | 値 |
|---|---|---|---|
| 0〜11 | | 共通ヘッダ | type = 2 |
| 12 | u8 | level | `0` = 情報、`1` = 警告、`2` = エラー |
| 13 | u8 | reserved | `0` |
| 14 | u16 | length | 文字列のバイト数 n(0〜200) |
| 16 | u8[n] | text | 文字列。印字可能な ASCII(0x20〜0x7E)だけ。終端の NUL はない |

- ペイロードの長さは 16 + n とちょうど一致しなければならない
- n の上限 200 は送信側の保証。受信側は、長さが整合していれば n > 200 でも拒否しない(下記「範囲と構造」)
- 送信側は 200 バイトを超える文字列を切り詰め、印字可能な ASCII 以外を `?` に置き換える。受信側は念のため、表示するときに制御文字を無害化してよい(拒否はしない)
- ファームウェアは、バイナリの出力中の読み出しエラーなど、テキストの出力中なら 1 行で表示する内容をこれで送る

## 種別 3: 状態

| オフセット | 型 | 名前 | 値 |
|---|---|---|---|
| 0〜11 | | 共通ヘッダ | type = 3 |
| 12 | u8 | side | このあと送る測距フレームの side(4 / 8) |
| 13 | u8 | targets_per_zone | 同じく T(1〜4) |
| 14 | u16 | field_mask | 同じく field_mask(予約ビットは立たない) |
| 16 | u8 | ranging_hz | 測距の頻度 [Hz](設定値) |
| 17 | u8 | flags | bit0 = flip_h、bit1 = flip_v(ファームウェアの表示の反転)。**bit2〜7 は 0**(立っていたら拒否) |
| 18 | u32 | i2c_hz | センサーとの I2C の実際のクロック [Hz] |
| 22 | u32 | sensor_read_bytes | センサーから 1 フレームで読むバイト数(ULD の data_read_size。I2C の負荷の目安) |
| 26 | u8 | fw_len | ファームウェアの版の文字列のバイト数 n(0〜64) |
| 27 | u8[n] | firmware_version | 版の文字列(印字可能な ASCII、終端なし) |

- ペイロードの長さは 27 + n とちょうど一致しなければならない
- fw_len の上限 64、ranging_hz、i2c_hz、sensor_read_bytes の値の範囲は送信側の保証。受信側はこれらの値では拒否しない(下記「範囲と構造」)
- 送信のタイミング: バイナリの出力に入った直後に 1 回。バイナリの出力中に `h` / `v` で反転を変えたときにも送る
- 測距フレームは自分のヘッダに side / T / field_mask を持つので、状態を受け取っていなくても解析できる。状態は表示の初期設定と情報表示のため

## CRC-32

パケットの最後の 4 バイト。**ペイロード全体**(共通ヘッダの先頭から本体の最後まで)に対して計算し、**リトルエンディアン**で付ける。

| 項目 | 値 |
|---|---|
| 名前 | CRC-32(IEEE 802.3、ISO-HDLC。zlib の `crc32`、JavaScript の多くの `crc32` 実装と同じ) |
| 多項式 | `0x04C11DB7`(反転した表現 `0xEDB88320`) |
| 初期値 | `0xFFFFFFFF` |
| 入力の反転(RefIn) | あり(各バイトを LSB から処理する) |
| 出力の反転(RefOut) | あり |
| 最終 XOR | `0xFFFFFFFF` |
| チェック値 | ASCII の `"123456789"` で `0xCBF43926` |

ビットごとの計算の例:

```
crc = 0xFFFFFFFF
for each byte b:
    crc ^= b
    repeat 8 times: crc = (crc >>> 1) ^ (0xEDB88320 if (crc & 1) else 0)
crc ^= 0xFFFFFFFF
```

## COBS(USB シリアル)

Consistent Overhead Byte Stuffing(Cheshire & Baker)。パケットから 0x00 をなくし、0x00 をメッセージの区切りに使えるようにする。

### エンコード

入力を「0x00 で終わるブロック」に分け、各ブロックを「コード 1 バイト + 0x00 以外のデータ」にする。

- コード k(1〜254)は、後ろに k − 1 バイトのデータが続き、その後に元は 0x00 があったことを表す
- コード 0xFF は、後ろに 254 バイトのデータが続き、その後に 0x00 は**ない**ことを表す(0x00 を含まない長い並びを 254 バイトずつ区切る)
- 入力の最後のブロックの後ろには 0x00 はない(デコードで付け足さない)
- この形式の決まり: **入力が「0x00 を含まない 254 バイトのブロック」でちょうど終わるときは、後ろに `0x01` を足さない**(Wikipedia の例と同じ。例: 254 バイトの `01 02 … FE` → `FF 01 02 … FE`)

```
code_pos = 0; out = [placeholder]; code = 1
for i, b in enumerate(input):
    if b == 0:
        out[code_pos] = code; code_pos = len(out); out.append(placeholder); code = 1
    else:
        out.append(b); code += 1
        if code == 0xFF:
            out[code_pos] = 0xFF; code = 1
            if i is the last index: return out      # 後ろに 0x01 を足さない
            code_pos = len(out); out.append(placeholder)
out[code_pos] = code
return out
```

例(テストベクタの `cobs` と同じ):

| 入力 | 出力 |
|---|---|
| (空) | `01` |
| `00` | `01 01` |
| `11 22 00 33` | `03 11 22 02 33` |
| `11 22 33 44` | `05 11 22 33 44` |
| `11 00 00 00` | `02 11 01 01 01` |
| `01 02 … FE`(254 バイト) | `FF 01 02 … FE` |
| `01 02 … FE FF`(255 バイト) | `FF 01 02 … FE 02 FF` |

### デコード

```
out = []; i = 0
while i < len(packet):
    code = packet[i]; i += 1
    if code == 0 or i + code - 1 > len(packet): reject
    append packet[i : i+code-1] to out (その中に 0x00 があれば reject); i += code - 1
    if code != 0xFF and i < len(packet): out.append(0x00)
```

- デコーダは、最後の 254 バイトのブロックの後ろに余分な `0x01` がある符号化(`FF 01 … FE 01`)も受け付ける(結果は同じ。テストベクタの `cobs_decode_only`)

### 長さ

- エンコード後の長さの最大: 入力 n ≥ 1 バイトで **n + ⌈n / 254⌉**、n = 0 で 1(0x00 を含まない入力で最大になる)
- 版 1 のペイロードの最大は 2642 バイト(8x8、T = 4、全フィールド)。パケット(+ CRC)は 2646 バイト、COBS 後は最大 2657 バイト、区切りを含めて **2658 バイト**。受信側は、区切りが来ないまま 2657 バイトを超えたら、次の 0x00 まで読み捨ててよい
- いまのファームウェア(8x8、T = 1、全フィールド)は、ペイロード 914 + CRC 4 = 918 バイト、COBS 後は最大 922、区切りを含めて最大 **923 バイト**/フレーム。15 Hz で約 13.8 KB/s

## 受信側の手順

USB シリアルの受信バイト列を 0x00 で区切り、区切られた各パケットについて次の順に検査する。どれかに当てはまったら、そのパケットは**拒否**する(捨てて数える。次の 0x00 から続ける)。テストベクタの `invalid` の `reject` は、この表の「理由」の語。

| 順 | 検査 | 理由 |
|---|---|---|
| 0 | 0x00 が続いた(長さ 0 のパケット) | **無視**(エラーとして数えない。`ignore`) |
| 1 | COBS のデコードに失敗(コード 0x00、コードが終わりを越える、途中に 0x00) | `cobs` |
| 2 | デコード後が 4 バイト未満 | `length` |
| 3 | CRC-32 が一致しない | `crc` |
| 4 | ペイロードが 12 バイト未満 | `length` |
| 5 | magic が `V8` でない | `magic` |
| 6 | version が 1 でない | `version` |
| 7 | type が 1〜3 でない | `type` |
| 8 | 測距フレーム: 18 バイト未満 | `length` |
| 9 | 測距フレーム: side が 4 / 8 でない、T が 1〜4 でない、field_mask に予約ビット(6〜15)、reserved が 0 でない | `frame_header` |
| 10 | 測距フレーム: 長さが式と一致しない | `length` |
| 11 | ログ: 16 バイト未満 | `length` |
| 12 | ログ: level が 3 以上、reserved が 0 でない | `log` |
| 13 | ログ: 長さが 16 + length と一致しない | `length` |
| 14 | 状態: 27 バイト未満 | `length` |
| 15 | 状態: side / T / field_mask が測距フレームと同じ範囲外、flags の bit2〜7 が立っている | `status` |
| 16 | 状態: 長さが 27 + fw_len と一致しない | `length` |

- 最初の 0x00 より前に受け取ったバイト(接続した時点で流れていた途中のデータや、テキスト表示の残り)は、パケットとして扱わずに捨てる
- 黙って読み違えないことを優先する。未知の版・種別・フィールドのビットは、推測で読まずに拒否する

### 範囲と構造

- 受信側が拒否するのは、上の表の**構造の誤り**(読み違えの原因になるもの: 長さの不整合、未知の版・種別・ビット、形の範囲外の side / T、予約バイト)だけ
- 値の範囲(ログの length ≤ 200、fw_len ≤ 64、ranging_hz、i2c_hz、sensor_read_bytes、測距値そのもの)は送信側の保証で、受信側はこれらでは拒否しない。長さが整合していれば受け付ける

## モードの切り替え(USB シリアル)

ファームウェアは起動時は**テキスト表示**(人がターミナルで見る形。ANSI エスケープを含む)。受信側は 1 文字のコマンドを送って切り替える。

| 送る文字 | 動作 |
|---|---|
| `b`(0x62) | バイナリの出力に切り替える。ファームウェアはまず **0x00 を 1 バイト**送り(それまでのテキストの残りを区切るため)、続けて**状態メッセージ**を送り、以後は測距フレームを送る。バイナリの出力中にもう一度 `b` を送ると、0x00 と状態を送り直す |
| `t`(0x74) | テキスト表示に戻す |
| `h` / `v` | 表示の左右 / 上下の反転を切り替える。バイナリの出力中なら新しい状態メッセージを送る |

- バイナリの出力中は、ANSI エスケープやテキストを一切混ぜない(ログは種別 2 で送る)。テキスト用のコマンド(`c`、`?`)は無視する
- 大文字(`B` / `T` / `H` / `V`)も同じ
- 受信側は接続したら `b` を送り、最初の 0x00 までを捨ててから解析を始める
- `b` を送ってもメッセージ(0x00 と状態)が来ない場合は、ファームウェアがまだテキスト表示のまま(`b` が届いていない。DTR や接続を確認)か、センサーの初期化に失敗して止まっている(赤 LED が点き、テキストで `FAILED: ...` を 2 秒ごとに出し続ける状態。この状態ではキーを受け付けない)ことを疑う
- **DTR を立てること。** Pico SDK の USB CDC は、ホストが DTR を立てていないと「未接続」とみなして何も送らない(`stdio_usb_connected()` は DTR を見る)。Web Serial では `port.setSignals({ dataTerminalReady: true })` を明示的に呼ぶのが確実(`open()` で既定で立つかは未確認)
- ボーレートの設定は関係ない(USB CDC)

## 送信側の制約(受信側が知っておくこと)

ファームウェアは USB の送信 FIFO(64 バイト)に空きができるのを待ちながら 1 つのメッセージを書く。SDK は、**最後に FIFO へ書けた時刻**から 500 ms(`PICO_STDIO_USB_STDOUT_TIMEOUT_US`)たっても空かなければ、そのメッセージの残りを捨てて戻る。その間ファームウェアの測距ループは止まる。受信側から見た結果は、ホストの状態で次のように分かれる。

- **完全に止まったホスト**(ポートを開いたまま読み取りを止めた): 詰まり始めに 1 回だけ最大 500 ms 止まり、以後は FIFO が空かないので各メッセージが待たずに捨てられる(測距は続く)。読み取りを再開すると、そのとき書き始めたメッセージの途中から届くことがあり、COBS / CRC の拒否として現れ、次の 0x00 から回復する。捨てたメッセージの分は seq が飛ぶ
- **遅いホスト**(読むが、送信の速さ 約 13.8 KB/s に追いつかない): FIFO に少しでも書けるたびに「最後に書けた時刻」が更新されるので、捨てられずに待ち続ける。FIFO が満杯になるたびに最大 500 ms まで待つので、**測距ループが繰り返し止まり、その間のセンサーのフレームは読まれない**(メッセージが作られないので seq は飛ばない)。この取りこぼしは測距フレームの timestamp の間隔で分かる(上の「シーケンス番号」)
- ポートを閉じた(DTR が落ちた): SDK は未接続とみなして待たずに捨てる。止まらない
- 詳しい数値は [design-notes.md](design-notes.md) の「設計メモ(Step 3)」

## テストベクタ(`docs/frame-vectors.json`)

`tools/gen_frame_vectors.py` が作る(C の実装とは別に Python で書いたエンコーダ)。C のホストテスト(`tests/test_frame_proto.c`)は、同じ入力から C で組み立てたバイト列がここと一致することを検査し、`tools/verification/decode_capture.py`(別に書いたデコーダ)はここをデコードして期待値と一致することを検査する。受信側の実装もこのファイルで検査する。

バイト列はすべて小文字の 16 進文字列(区切りなし。空は `""`)。

**同期の前提**: `messages` と `invalid` の `serial_hex` は、**同期済みの状態(直前に 0x00 を受けた状態)から流す**前提のバイト列で、先頭に 0x00 はない。受信側のストリーム解析(最初の 0x00 までを捨てる処理)に通してテストするときは、**先頭に `00` を 1 バイト足す**。`streams` の `serial_hex` は逆に、ポートを開いた直後のような**同期していない状態から**流す前提で、先頭から最初の 0x00 までは捨てる対象になる。

```jsonc
{
  "description": "...",
  "format_version": 1,
  "crc32_check": { "input_ascii": "123456789", "crc32": "cbf43926" },  // crc32 は 8 桁の 16 進
  "cobs": [                       // エンコードとデコードの両方向で一致すること
    { "name": "...", "decoded_hex": "...", "encoded_hex": "..." }       // encoded_hex は区切りの 00 を含まない
  ],
  "cobs_decode_only": [           // デコードだけ一致すること(正規でない符号化)
    { "name": "...", "note": "...", "encoded_hex": "...", "decoded_hex": "..." }
  ],
  "messages": [                   // 正しいメッセージ
    {
      "name": "...",
      "payload_hex": "...",       // ペイロード
      "crc32": "xxxxxxxx",        // ペイロードの CRC-32
      "serial_hex": "...",        // USB シリアルに流れるバイト列(COBS + 最後の 00。途中に 00 はない)
      "expect": { ... },          // serial_hex をデコードした結果(下記)
      "input_text": "...",        // ログだけ: 送信側に渡した文字列(切り詰め前)
      "input_firmware_version": "..."  // 状態だけ: 同上
    }
  ],
  "invalid": [                    // 拒否(または無視)すべきバイト列
    { "name": "...", "reject": "crc", "serial_hex": "..." }             // reject は「受信側の手順」の理由の語
  ],
  "streams": [                    // 複数のメッセージを連結したバイト列と、期待する統計(同期していない状態から流す)
    {
      "name": "...",
      "description": "...",
      "serial_hex": "...",
      "expect": {
        "leading_bytes": 6,       // 最初の 0x00 より前で捨てたバイト数
        "trailing_bytes": 0,      // 最後の 0x00 より後の(区切られていない)バイト数
        "empty_packets": 0,       // 長さ 0 のパケット(0x00 が続いた)の数。最初の 0x00 より前は数えない
        "accepted": 4,            // 受け付けたメッセージの数
        "accepted_by_type": { "frame": 4, "log": 0, "status": 0 },
        "rejected": { "crc": 1 }, // 拒否した数を理由別に(拒否がなければ {})
        "accepted_seqs": [ ... ], // 受け付けたメッセージの seq を受け付けた順に
        "gaps": 0,                // 欠落の回数(「シーケンス番号」の 1 ≤ d < 2^31 の回数)
        "missing_messages": 0,    // 欠落数の合計(d の合計)
        "backward": 0             // 後退の回数(d ≥ 2^31)
      }
    }
  ]
}
```

`expect` の形(キーは種別ごとに固定。数値は 10 進の JSON 数値):

- 測距フレーム: `{"type": "frame", "seq", "timestamp_us", "side", "targets_per_zone", "field_mask", "temperature_c", "fields": {"distance_mm": [...], "target_status": [...], "range_sigma_mm": [...], "nb_target_detected": [...], "signal_per_spad": [...], "nb_spads_enabled": [...]}}`。`fields` には field_mask に含むものだけがある。配列の並びは上の「配列の並び」のとおり
- ログ: `{"type": "log", "seq", "timestamp_us", "level", "text"}`
- 状態: `{"type": "status", "seq", "timestamp_us", "side", "targets_per_zone", "field_mask", "ranging_hz", "flags", "i2c_hz", "sensor_read_bytes", "firmware_version"}`

`invalid` の各項目は、狙った検査だけが失敗するように作ってある(例: `bad_magic` は magic だけを変え、CRC は付け直してある)。`serial_hex` は最後に 00 を含む 1 パケット(`empty_packet` は `00` だけで、`ignore`)。

収録しているメッセージ: 4x4 全フィールド(値の境界: 負の距離、0、65535、u32 の最大など)、8x8 全フィールド(ファームウェアが送る形。seq と timestamp は折り返し直前)、4x4 の距離とステータスだけ(上の「例」)、4x4 で T = 2(ターゲットごととゾーンごとの配列の長さの違い)、8x8 で T = 4 の全フィールド(版 1 の最大長 2642 バイト)、ログ 2 つ(210 文字を 200 に切り詰めるものを含む)、状態。

収録している `invalid`(名前: 理由): `empty_packet`: ignore、`cobs_code_past_end`: cobs、`crc_mismatch`: crc、`decoded_short`(COBS デコード後 3 バイト): length、`too_short`(ペイロード 3 バイト): length、`bad_magic`: magic、`bad_version`: version、`unknown_type`: type、`frame_bad_side` / `frame_bad_targets` / `frame_reserved_field_bit`(マスク 0x007F)/ `frame_reserved_field_bit_high`(マスク 0x803F)/ `frame_reserved_nonzero`: frame_header、`frame_header_short`(17 バイト)/ `frame_length_short` / `frame_length_long`: length、`log_header_short`(15 バイト): length、`log_bad_level` / `log_reserved_nonzero`: log、`log_length_mismatch`: length、`status_header_short`(26 バイト): length、`status_bad_side` / `status_bad_targets` / `status_reserved_field_bit`(マスク 0x007F)/ `status_bad_flags`: status、`status_length_mismatch`: length。

収録している `streams`: `leading_garbage_and_seq_wrap`(先頭に 6 バイトのテキスト、seq が FFFFFFFE → FFFFFFFF → 0 → 1 と折り返す。欠落なし)、`gap_and_backward`(seq 10, 11, 14, 5, 6。欠落 1 回・2 個、後退 1 回)、`rejects_empty_and_partial`(seq 20 のフレーム、長さ 0 のパケット、CRC 不良の seq 21、COBS の誤り、seq 22 のフレーム、23 のログ、24 の状態、最後に区切られていない 5 バイト。拒否した 21 は 20 → 22 の欠落 1 個として数える)。期待値は組み立て方から手で数えたもの。

## 版の扱い

- この文書は版 1。ペイロードの形(ヘッダ・フィールドの並び・型)を変えるときは version を上げる。フィールドのビットを新しく定義するときも上げる(版 1 の受信側は予約ビットを拒否するので、黙って読み違えない)
- 受信側は version が自分の知っている値でなければ拒否する
- リンク層(CRC-32、COBS、0x00 区切り)は版に含めない。変えるときは経路の定義として別に決める
